# 采集与读取细节

## 构造有限应用入口

定位最终JIT而不是只看测试文件名。若原测试带autotune/profiler循环，可以在任务目录另建调用原JIT的最小入口，固定被选配置、输入和grid，并独立检查输出。调用`.fn`等包装层的方式随项目改变，先核其实际对象，不把多次`.fn.fn`当通用API。

已有ELF重放应绑定自己的ABI；旧固定NSA/MoE driver只能用作理解实例，不能直接拿另一算子的signature、buffer或grid替换名称运行。需要确认metadata、hidden参数与实际shared C++ launcher。

捕获目的决定范围：单core小例适合验证局部时序，跨block/双V协议需要对应完整供给；只截core0不能自动代表整个grid。故障微例可删payload，但保留被检验的通知、代次、资源和退出关系。

## CLI 发现与边界

历史CANN环境出现过 `msopprof simulator` 和 `msprof op simulator` 两种入口，参数不可混用。先从当前CANN工具位置及其帮助/现有成功命令确认SoC、kernel筛选、输出、启动次数及超时单位，再运行本任务的应用命令。真实命令保存为argv或准确脚本，不将占位示例直接当可执行命令。

优先使用本任务已有、可审查的执行器：控制整棵自有进程树，记录PID身份、开始时间、时间/目录字节限额和停止原因；超时后核对是否真的退出，再决定后续任务。不要为抓流水常驻轮询其他容器或重复探测驱动。

采集预算包括原始dump、中间bin、解析副本及输入/缓存；最终归档大小可能只是峰值一部分。目录`st_size`、磁盘块、IO字节、RSS、文件cache和SHM不是同一计量；按运行器实际统计字段命名。

## 产物索引

可按任务实际输出保存以下类别，不强制使用目录名：

| 类别 | 至少能回答的问题 |
|---|---|
| run身份 | 哪个应用、特化、grid、ELF、工具、命令、尝试 |
| 输入与数值 | 参考/seed、活动输出、未写区和检查结果 |
| stdout/stderr/status | 是否执行目标、超时点、异常与清退范围 |
| 原始流水 | 哪个core、pop/issue/completion、PC/指令字及动态ID |
| bin/时间线 | 当前viewer实际应打开哪个文件，来自哪份原始捕获 |
| 解析与诊断 | parser版本、缺失记录、时间变换、结论适用范围 |

发现目标已完成而导出失败时，先查原始记录完整性；可以另存一次只读解析恢复，不覆盖原失败。数据截断、未绑定ELF或缺少peer时，只能做局部诊断，不升级为完整执行证据。

## 在图中证明时序

先选择相同捕获/角色/ID，记录viewer的显示start/end和raw时间。offset或归一化可能解释“图上4µs、raw7µs”的差异，但应由元数据/同一事件对应确认，不凭截图猜固定偏移。不同core频率、cycle单位与公共时钟是否可比需核对。

对于“旧WAIT未完成，TRY又允许新WAIT”，建立事件表：

```text
旧WAIT：接收角色 / ID / PC / 动态ID / 提交与完成点
TRY：目标ID来自立即数还是寄存器 / 查询返回值或可证明的分支
新WAIT：同一接收通知和相关代次 / 提交点
SET：供给该通知的peer / 生效及被观察的边界
```

若日志只显示WAIT开始执行时间，不显示入队/提交时间，两个条不重叠不能排除提前排队；两个同名WAIT也不能单独证明多领取。查询点落在旧WAIT可见扣减前需要相应记录支持；“完成”字段是否代表counter对TRY可见仍可能是ISA/工具未证明项。

奇偶slot可能是3/7，两个V peer可能是3/19；它们不是两条相同counter的WAIT。同一数字ID在不同接收core也不应合并计数。FLOWCTRL是viewer分类时，scalar指令可能画在该行；寻找TRY可用符号/PC和原始指令日志，不只看SCALAR行。

映射到IR时带上计算块、tile/逻辑任务、slot/代次与真实地址，解释为何该块合法进入、发了什么及什么尚未完成。静态编排、提交前进、pipe执行与counter取样分开；不要把跨pipe超前直接称为scalar自身乱序。
